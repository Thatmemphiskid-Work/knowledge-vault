# Attacker Vantage and Discovery

## Questions before commands
- Starting position: outside the network, inside a segment, authenticated user or local unprivileged account?
- Which interfaces and protocols are reachable from that position?
- What product/version evidence is externally visible, and what requires privileged inventory?
- Does the CVE require authentication, user interaction, a specific feature, local access or a particular architecture?
- What observable result distinguishes the weakness from normal behavior or a different fault?

## Single-asset service discovery
Run from a bench machine with Nmap already installed. Replace the documentation-only IP with the one bench asset being assessed. This discovers services; it is not a CVE verification.

```sh
nmap -sT -sV --version-light -p 22,80,443,445,3389,8080 -oA discovery 192.0.2.10
curl --head --connect-timeout 5 --max-time 10 https://asset.example
```

That port list is deliberately explicit and incomplete. Add the known application's actual ports; missing results on this list do not establish absence. `-sT` needs no raw-packet privilege on typical hosts. Save all three Nmap outputs generated by `-oA`. Reverse proxies and banners can hide the actual backend version.

## VoIP example: discovery, not exploit proof
The supplied VoIP book discusses SIP signaling discovery on PDF page 41 and notes that media uses other ports. Keep the test to a single asset instead of copying the book's example large subnet scan.

```sh
# UDP scanning generally needs elevated privileges.
nmap -sU -sV --version-light -p 5060 -oA sip-discovery 192.0.2.10
```

`open|filtered` is ambiguous; determine actual SIP service presence separately. This does not establish any SIP-specific CVE. See [[book-10]], PDF page 41.
